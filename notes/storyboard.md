# Q&A 플랫폼 소개 — 발표 구성과 대본

대상: 현업 담당자, 임원진, 같은 부서 동료. 개발 지식 없이 이해할 수 있는 소개 발표.
분량: 약 10~12분 + 질의응답.

핵심 메시지: **여러 곳에 흩어진 문의를 한곳에 모으고, 관련 작업을 연결해 담당자와 개발자가 해결까지 함께 소통한다.**

## 기승전결

- 기: 문의가 여러 서비스에 흩어져 있으면 찾고, 담당자를 확인하고, 진행 상황을 다시 물어야 한다.
- 승: Q&A 플랫폼은 문의·담당자·답변·내부 논의·진행 상황을 한곳에 모은다.
- 전: 문의와 해결 작업을 연결한다. 진행하며 부딪힌 사례를 통해 업무 기준을 어떻게 정리했는지 소개한다.
- 결: 담당자와 개발자가 같은 기록을 보고 해결까지 이어 가는 업무 흐름을 만든다.

## 슬라이드별 발표 대본

### 1. 왜 Q&A를 한곳에서 관리해야 할까요?

문의는 들어오는 곳도, 확인하는 사람도, 처리 기록을 남기는 곳도 제각각일 수 있습니다. 그래서 담당자를 찾고 지난 내용을 다시 확인하는 데 시간이 듭니다. Q&A 플랫폼은 이 흩어진 과정을 한곳으로 모으기 위해 만들었습니다.

### 2. 기존에는 문의와 처리 기록이 나뉘어 있었습니다

서비스마다 문의를 따로 확인하고, 담당자와 답변, 개발 요청의 진행 상황도 여러 곳에서 관리했습니다. 문의가 어디까지 처리됐는지 알기 위해 화면을 옮겨 다니거나 동료에게 다시 물어야 했습니다.

### 3. Q&A 플랫폼은 문의부터 해결까지 잇는 업무 공간입니다

사용자는 익숙한 서비스에서 문의를 남깁니다. 담당자는 통합 관리 화면에서 문의를 확인하고 답변합니다. 개발이 필요한 내용은 해결 작업과 연결해 개발자와 진행 상황을 공유하고, 결과를 다시 문의자에게 안내합니다. 모든 문의가 개발 작업으로 넘어가는 것은 아닙니다.

### 4. 문의가 해결되는 흐름은 이렇습니다

담당자가 문의를 확인하고, 바로 답할 수 있으면 답변합니다. 수정이 필요하면 해결 작업을 연결하고 개발자와 처리 상황을 공유합니다. 작업이 끝난 뒤 담당자가 결과를 확인해 문의자에게 안내합니다.

### 5. 한곳에서 관리하면 이런 점이 달라집니다

현업 담당자는 문의와 이전 답변을 한 번에 찾고, 개발자는 어떤 요청에서 시작된 작업인지 함께 확인할 수 있습니다. 책임자와 동료는 남은 문의와 진행 상황을 파악하기 쉬워집니다. 이는 기대 효과이며 시간 절감이나 누락 감소를 측정한 수치는 아직 없습니다.

### 6. 진행하며 부딪힌 점 ① 같은 문제인데 문의는 여러 건

예를 들어 여러 사람이 같은 파일 열기 오류를 각각 문의할 수 있습니다. 문의마다 별도 개발 작업을 만들면 같은 일을 중복해서 처리할 수 있고, 한 문의만 연결하면 다른 문의의 처리 상황을 놓칠 수 있습니다.

### 7. 해결 방법: 관련 문의를 작업 하나에 연결하기

같은 원인에서 나온 문의는 공통 해결 작업 하나에 함께 연결하도록 정리했습니다. 개발자는 작업 하나를 처리하고, 담당자는 연결된 문의를 각각 확인해 결과를 안내합니다. 반대로 한 문의에 여러 작업이 필요한 경우도 연결할 수 있습니다.

### 8. 진행하며 부딪힌 점 ② 개발 완료와 문의 해결은 다릅니다

개발 작업이 끝났다고 문의자에게 결과가 전달된 것은 아닙니다. 결과 확인과 답변이 빠지면 문의자는 여전히 해결 여부를 모를 수 있습니다. 그래서 개발 작업의 진행과 문의의 처리를 각각 확인하고, 담당자가 결과를 안내하는 단계를 두었습니다.

### 9. 진행하며 부딪힌 점 ③ 내부 협의와 사용자 안내를 구분하기

담당자끼리 공유해야 할 확인 내용과 문의자에게 보내는 답변은 목적이 다릅니다. 이를 한데 기록하면 내부 논의가 잘못 공개되거나, 인수인계에 필요한 내용이 빠질 수 있습니다. 같은 문의 안에서 내부 메모와 공개 답변을 나눠 기록하도록 정리했습니다.

### 10. 문의는 한곳에, 해결까지 소통은 이어지게

이번 플랫폼의 핵심은 문의를 모으는 데서 끝나지 않습니다. 관련 작업과 담당자, 진행 상황, 결과 안내를 연결해 현업과 개발자가 같은 내용을 보고 해결까지 이어 가는 것입니다.

## 표현 원칙

- ‘이슈’는 처음에 ‘문의를 해결하기 위한 작업’이라고 설명하고, 이후에는 쉬운 표현을 우선한다.
- API, DB, 인증, 코드 등의 기술 설명은 발표에서 제외한다.
- 실제 제품 화면이 아닌 문서 기반 설명 도식은 실제 화면처럼 소개하지 않는다.
- 파일 열기 오류는 이해를 돕기 위한 가상 사례라고 밝힌다.
- 개선 효과는 기대 효과로 표현하며, 측정되지 않은 시간 절감·누락 감소 수치를 말하지 않는다.
- 진행 경험은 문서에 기록된 업무 판단과 처리 기준을 바탕으로 설명한다.

| 모든 서비스가 이미 연결되어 있나요? | 자료만으로 전체 서비스의 연결 완료를 확인할 수는 없습니다. 실제 적용 범위를 별도로 확인해야 합니다. |
